# Game Design Review Guide

担当と権限は [ROLES.md](ROLES.md)。[PRODUCT.md](PRODUCT.md) と [現在のスプリント](../../plans/current-sprint.md) を基準に、ゲームデザインだけを評価する。レビューは問題を作り出すための工程ではない。

## 入力

Goal・Context・Scope・Non-goals、基準と対象差分、関連仕様、Producerの実プレイ感想、利用できる画像・動画・検証結果を読む。技術説明やPASSだけから体感を推定しない。未実装の案をレビューする場合は、観察事実と実装後に確認する仮説を分ける。

## 観点

- **Game feel**：仕込み→位置取り→灰縫い→次の仕込みのテンポ、手応え、連続攻撃の気持ちよさ。
- **理解・Readability**：灰紋、経路、成功、着地後の危険、次の行動が伝わるか。
- **リスク / リターン**：動いて狙う・突破する危険に意味があり、安全な待機だけが有利にならないか。
- **ビルド多様性**：拡散・濃縮・連続・混成に異なる判断があるか。通常の1ランで全取得を前提にしていないか。
- **支配的戦略と強弱**：特定の強化・仕込み方・攻撃ループだけが他の選択を押しのけないか。
- **アップグレード相乗効果**：取得後に次の候補やプレイの変化を想像できるか。「壊れた」強さを楽しみながら他の選択にも理由があるか。
- **認知負荷**：追う情報と操作が増えすぎていないか。初見と経験後の両方で確認する。

コード構成・save/load・入力イベントの実装・テスト不足はQAへ渡す。不具合らしい事実は再現できる情報を添えてQAへ渡し、それを前提にした新しいバランス要件を発明しない。

## 出力テンプレート

```markdown
Reviewer: <担当・会話。独立レビューか自己確認か>
Target: <スプリント名、基準コミット、対象差分または仕様案>
Evidence: <実際に読んだ資料・見た画像・プレイ記録。未確認も記載>

Verdict: 重大な懸念なし / 要修正 / 判断保留
Major concerns: <なければ「なし」>
Minor concerns: <なければ「なし」>
Player-facing risks: <体感・理解・認知負荷への影響。なければ「なし」>
Dominant strategy risks: <選択を支配する懸念。なければ「なし」>
Questions for Producer: <採否や実プレイ判断に必要な問いだけ。なければ「なし」>
Recommendation: <現Scopeで進行可 / Scope内で修正 / 次回候補 / 実プレイで判断>
```

指摘ごとに「対象場面→根拠→プレイヤーへの影響→Scope内の対処または観察項目」を短く書く。確認済みの事実と仮説を明記する。Majorは目標・コア体験・選択を大きく損なう懸念、Minorは進行を妨げない改善候補。未プレイを理由に一律に問題扱いせず、実プレイで判断する部分を残す。

## 最小の依頼例

> Game Design Reviewerとして、PRODUCT.mdとplans/current-sprint.md、および渡した差分をこのガイドでレビューしてください。技術品質はQAへ分け、重大な懸念がなければそう記録してください。

レビュー結果はDirectorが [WORKFLOW.md](WORKFLOW.md) に沿って統合する。Recommendationは提案であり、Producerの最終判断や実装・公開の許可を代替しない。
